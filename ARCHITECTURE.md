# Architecture

> **Status:** built from [PLAN.md](PLAN.md), all seven phases; the end-to-end check on real accounts is the last step. This file describes the code as it is: update it with every change that affects it.

## Overview

```
 Browser (http://127.0.0.1:4747)
        │
        ▼
 Express server (bound to 127.0.0.1 only; also serves the built client)
   ├── Data sources ──► OSRS Hiscores (Jagex)
   │                ──► Wise Old Man API
   │                ──► TempleOSRS API
   │                ──► OSRS Wiki (MediaWiki API, Bucket, prices API, images)
   │                ──► RuneLite item icons
   │                ──► Character Export JSON files (filesystem)
   ├── SQLite (accounts, snapshots, cache, goals, chats, settings)
   └── AI provider ─► Claude Agent SDK (Claude Code) ──► Claude (plan or API key)

 RuneLite + Character Export plugin ──► .runelite/character-exporter/<name>/*.json
 RuneLite + Temple OSRS plugin ──────► TempleOSRS (collection log sync)
```

The server exists because the Jagex hiscores send no CORS headers (the browser can't call them directly) and because Claude credentials must stay out of the browser.

## Platforms

Runs on Windows, macOS, Linux and WSL. Developed on WSL; the finished app will likely run on Windows.

- **Scripts:** npm scripts use only Node and cross-platform tools. Environment variables set in scripts go through `cross-env`, `.env` is loaded with Node's `--env-file-if-exists`, and paths are built with Node's `path`.
- **App data** (SQLite database, caches) lives in the OS's app-data folder: `%LOCALAPPDATA%\wise-old-model` on Windows (or `<home>\AppData\Local\wise-old-model` without `LOCALAPPDATA`), `~/Library/Application Support/wise-old-model` on macOS, `$XDG_DATA_HOME/wise-old-model` or `~/.local/share/wise-old-model` on Linux and WSL (a relative `XDG_DATA_HOME` is ignored, per the XDG spec). `DATA_DIR` overrides it. On WSL this keeps SQLite off the Windows drive, where its file locking isn't reliable.
- **RuneLite folder** defaults to `~/.runelite`, where RuneLite keeps it on every OS. `RUNELITE_DIR` overrides it; on WSL with RuneLite on Windows it's `/mnt/c/Users/<user>/.runelite`.
- **Folder settings** (`DATA_DIR`, `RUNELITE_DIR`): empty means the default; a leading `~` means the home folder; on Windows a WSL path such as `/mnt/c/Users/me/.runelite` becomes `C:\Users\me\.runelite`, so a `.env` shared with WSL keeps working. Anything else that wouldn't work on this OS (a Linux path on Windows, a Windows path on Linux or WSL, a relative path, a line break) stops the server with a message saying what to write instead.
- **Dependencies:** no native Node add-ons that compile on install (node-gyp). Tools that ship prebuilt per-OS binaries through npm (Vite, Biome, TypeScript 7, the Agent SDK's Claude Code) are fine.
- **No scheduled jobs:** the app only fetches data while you use it, so nothing depends on cron or Task Scheduler.
- **Watching for code changes** in development checks files' modified times once a second rather than waiting for file-change events, which WSL doesn't deliver for files on a Windows drive (`/mnt/c/...`); it works the same on every OS. Each check of the server's code costs about 10 ms of CPU there.
- **Switching OS:** moving one checkout between WSL and Windows needs a fresh `npm install`, because build tools like Vite ship per-OS binaries.

## Backend

- **Stack:** Node.js 26 (pinned in `mise.toml`), Express 5, TypeScript run directly by Node (see Repo and tooling).
- **Data sources:** one module per source, all sending requests through the shared request handler (see Data sources → Fetching and caching).
- **Local-only server:** binds to `127.0.0.1`. Every request must carry a `Host` of `localhost:<port>` or `127.0.0.1:<port>` (bare names too on port 80, which browsers omit), which blocks DNS-rebinding attacks from websites open in the same browser; requests the browser marks as coming from another site (`Sec-Fetch-Site` of `cross-site` or `same-site`, which covers pages on other localhost ports) are refused unless they open a page (a GET top-level navigation), so an `<img>` or `fetch()` on another site can't make the server do anything, such as fetch an icon; any request other than GET or HEAD must also carry a matching `Origin`. In development the Vite dev server's port 5173 is accepted as well, because the Vite proxy passes the browser's Host and Origin through. Failures get a 403 with a plain explanation.
- **Security headers** on every response: `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY` (no other site can frame the app and trick clicks onto its buttons), `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`.
- **Production serving:** files from `client/dist`; paths without a file extension get `index.html` (app pages); a missing asset gets 404; if the client isn't built, the server warns at startup and pages answer 503 with "run npm run build".
- **Startup:** the server claims its port first, so a second copy stops with "port in use" before it can touch the database; then it opens the database (migrating and backing up as needed), answering 503 "starting" meanwhile, and hands the port to the app.
- **Storage:** Node's built-in SQLite (`node:sqlite`, "release candidate" in Node 26), queried through [Kysely](https://kysely.dev) via a small adapter of our own (Kysely's SQLite dialect expects statements with a `reader` flag and array parameters; `node:sqlite` gives `columns()` and spread parameters). Schema changes are Kysely migrations. No compiled add-ons. Fetched data that changed is saved as a snapshot with the raw response, so parsers can be improved later without losing history.
- **API:** REST routes under `/api` for accounts (look up, add, rename, delete), account data (overview, this week, bank and gear, collection log), refresh and file checks, goals, chats (list, send, approve or decline, stop), settings and icons. Chat answers stream over SSE. The routes: `GET /api/health`; `GET /api/settings` and `PATCH /api/settings` (any subset of the settings; unknown keys and invalid values get a 400 with Zod's message, and nothing is saved); `GET /api/about` → `{ dataDir, runeliteDir, runeliteFound, characterExportFound, lastBackup, env }` (whether the RuneLite folder and its `character-exporter/` are there; the newest backup `{ file, at }` or null, one named in the future passed over unless it's the only kind there is; `env` is `CONTACT`, and `PORT`, `DATA_DIR` and `RUNELITE_DIR` as set, null when not, with `ANTHROPIC_API_KEY` only `set` or `not set`: the key never leaves the server); `POST /api/backups` → 201 `{ file, at }` (backs up now, as the daily backup does; a backup that can't be made is a 500 saying why, "Couldn't make the backup in <folder>: <reason>"); `GET /api/accounts` (by name); `GET /api/accounts/status` → each account's `{ id, characterExport: { found, lastWritten, error }, temple }` in the same order, from what's saved (no site is asked): whether its Character Export folder is there and when it was last written (`found` null, with why, when the RuneLite folder can't be read), and Temple's log as last fetched, a freshness (`notFound` when Temple had none for the name); `GET /api/accounts/lookup?name=` (what the hiscores and Wise Old Man know, whether the name has synced its collection log on TempleOSRS and when, and whether Character Export has written the name's files and when; `onHiscores`, `womTracked`, `temple.synced` and `characterExport.found` are null for a source that couldn't be checked, and `problems` says why, so an outage isn't reported as an unknown name); `POST /api/accounts` `{ name, type, trackOnWom }` → 201 `{ account, problems }` (Wise Old Man is asked about the name, and asked to start tracking only when it doesn't track it and the person chose to; its answer is saved, so the new account's first Overview doesn't ask again; Wise Old Man failing doesn't stop the add, but tracking that didn't start is listed in `problems`; 409 when the name matches an account already added); `PATCH /api/accounts/:id` `{ name?, type? }` (a rename keeps the history and forgets the old name's failures, so the next fetch asks under the new name; a type that differs from the saved one counts as set by hand); `DELETE /api/accounts/:id` (204; all its data goes too); `POST /api/accounts/:id/refresh` → `{ freshness, renameSuggestion }` (it reads the Character Export files too); `POST /api/accounts/:id/files/check` → `{ changed, missing, errors, goalsCompleted }` (reads the account's Character Export files that changed, see RuneLite data, and when one did, marks the goals its data shows reached as done); `GET /api/accounts/:id/collection-log` (`{ log, freshness, tabsError }`: Temple's log, fetched first when it's over an hour old, and how that fetch went; `log` is null when Temple has none for the name, or was down before it was ever fetched; `tabsError` says why Temple's category list couldn't be had, every entry then being under Other); `GET /api/accounts/:id/bank?search=` (the Bank and gear page's data, and what the search finds; a search is up to 100 characters, and an empty one is none); `GET /api/accounts/:id/overview` (the Overview page's data, after fetching the hiscores, Wise Old Man's player and Temple's collection log when they're past their freshness limits, and the wiki's combat achievement thresholds, which are kept a day); `GET /api/accounts/:id/gains?period=day|week|month` or `?start=&end=` (This week's data for one of its periods or a range of ISO times, start first; anything else is a 400); `GET /api/accounts/:id/goals` → `{ goals, freshness }` (the hiscores and Temple's log are fetched first when past their freshness limits and goals the data shows reached are marked done; each active goal comes with its `progress`); `GET /api/accounts/:id/goals/options` → what the Add goal dialog picks from (see Goals), each list `{ options, missing }`, `missing` saying what to do when its data isn't saved; `POST /api/accounts/:id/goals` `{ title?, target }` → 201 the goal; `PATCH /api/goals/:id` `{ title?, status?, position? }` → the goal (the page reloads the goals for their progress); `POST /api/accounts/:id/goals/reorder` `{ ids }` → the active goals in their new order (see Goals). A goal id is plain digits; an unknown one is a 404. Refresh, and a file check that read a changed file, mark goals the new data shows reached as done. `GET /api/accounts/:id/chats` (the account's chats that have messages, the most recently used first); `POST /api/accounts/:id/chats` → 201 an empty chat (the one made before, while it's still empty); `PATCH /api/chats/:id` `{ title }` (1 to 100 characters); `DELETE /api/chats/:id` (204; an answer in progress is stopped first); `GET /api/chats/:id/messages`; `POST /api/chats/:id/messages` `{ text, note? }` (the text 1 to 4,000 characters; the note, shown under the message when a page sent it, up to 100) → a `text/event-stream` of `ChatEvent`s, one `data: <json>` each (see AI layer), or a 409 while the chat is still answering; `POST /api/chats/:id/approvals/:requestId` `{ approve }` → 204, or a 404 when that change isn't waiting; `POST /api/chats/:id/stop` → 204. An unknown chat is a 404. `GET /api/chat/models?billing=` → `{ models, error }`: the models the provider lists for that billing (`plan` or `api_key`; without it, the one set), each `{ id, resolvedId, label, description, efforts }`, or none and why (Claude Code not signed in, say). Deleting an account stops its chats' answers first. Names must be 1 to 12 letters, numbers, spaces, hyphens or underscores, with at least one letter or number. An account id is plain digits; an unknown one is a 404. `GET /api/icons/wiki/:file` and `GET /api/icons/item/:id` (see Game icons).
- **Errors** answer in JSON (`{ "error": "..." }`, `ErrorAnswerSchema` in shared) like everything else, and only one place writes them: the last middleware, `jsonErrors`. Routes and the guard throw or pass on an `HttpError(status, message)`, and `parseInput(schema, body)` turns a body that doesn't fit into a 400 with Zod's message. An `HttpError` keeps its status and message whatever the status (Back up now's failure is a 500 saying why); another error meant for the client (marked `expose`: a body that isn't JSON or is too large) keeps its 4xx status and message. Another site's failure (a `SourceError` from the request handler, whose message names the site and says what went wrong) answers 502 with its message, so routes needn't catch it unless they treat it specially (the icon routes answer a missing icon with a 404). Anything else is a 500 that says to look at the server's console, where the details go, even when it carries a status (a missing file's path isn't the browser's business).

## Data sources

### How each source is used

| Source | Used for |
|---|---|
| Character Export | Everything in game: quests, diaries, combat achievements, bank, seed vault, inventory, gear, levels and XP |
| Official hiscores | Our own snapshots of levels, XP, ranks, boss kill counts and clue counts, with no third party in between |
| Wise Old Man | Gains over any period, EHP/EHB and time to max, achievements, history from before the app existed, and account type |
| OSRS Wiki | Search and page sections for cited answers; Bucket tables for quest requirements, combat achievements, gear stats, recommended gear and drop sources; the quest list for quest points |
| Wiki prices | GE prices and item info |
| TempleOSRS | Collection log: every item with count and date obtained, totals, last sync time and EHC. Needs the Temple OSRS RuneLite plugin (one manual sync, then automatic sync of new items). The hiscores' "Collections Logged" total is the backup number |

- In This week and `get_gains`, XP and kill gains come from Wise Old Man; quests, diaries and combat achievements completed come from our own snapshots; new collection log items come from Temple's dates. Our own hiscores snapshots keep an independent copy of the stats history. The 7 days are Wise Old Man's `week` period, saved with the account's other data (`wom_gains_week`); Today (from midnight in the settings' zone), 30 days and a range picked are asked for by start and end date, since Wise Old Man's `day` is the last 24 hours and its `month` a fixed 31 days (`2678400000` ms in its utils package), and are kept 15 minutes in the server's memory with the account's other remembered fetches (`remembered` in `server/src/services/freshness.ts`, under the same rules as a source's: a failure also waits 15 minutes, and a failure with an earlier answer gives that answer and why it's old). Refresh forgets those fetched, or failed, over a minute before, as it never fetches anything again within a minute, and a rename forgets them all; an account's id is never reused, so a deleted account's are never asked for again.
- **When a source fails,** the app keeps showing the last good data, marks it stale with the reason (shown next to the freshness times), and tools report it to the AI so it can say so.
- The app never updates Wise Old Man automatically. Refresh asks it to update a player only when its data is more than an hour old.
- Every outbound request sends a descriptive User-Agent with the contact info set in `.env`.

### Fetching and caching

- **Only when used.** Online data is fetched when it's needed (opening an account, a chat question that needs it, or Refresh), and only when the saved copy is older than its freshness limit. There is no background fetching and no scheduled job; the app only runs while you're using it.
- **Refresh** skips the freshness limits, but won't refetch a source fetched less than a minute ago, and still follows the Wise Old Man update rule above.
- **A failed attempt counts** toward the limit like a fetch, so a site that's down, or one that doesn't know the account (a 404), isn't asked again on every open: the last good data stays, reported stale with the reason (and `notFound` for a 404, which a rename suggestion uses), until the next attempt. The server remembers failures while it runs, including for a source never fetched, which has no row. A fetch already under way is shared, so two tabs or a page load during Refresh don't fetch twice, and an attempt dated more than a minute in the future (the clock went back) counts as due. Wise Old Man is contacted only when one of its kinds is due. On Refresh, if its player answer says it last updated the player over an hour ago, it's asked to update, and the update's answer (the updated player) is what's saved; its gains and achievements are read after the player answer, and not at all when it doesn't track the player, since they'd only be not found too. A player it doesn't track answers 404 first, so Refresh never starts tracking anyone. This is `ensureFresh` in `server/src/services/freshness.ts`, which knows nothing about any one source: each kind has a fetcher, told whether it's a Refresh, and a small table says which kinds wait for which on Refresh.
- **Snapshots:** a fetch whose data differs from the last one is saved exactly as received. Identical data isn't saved twice.

| Data | Kept for |
|---|---|
| Hiscores | 15 min |
| Wise Old Man reads | 15 min |
| Temple collection log | 1 hour |
| Temple's list of collection log categories | 1 day |
| GE prices (`/latest`, every item in one request) | 5 min |
| Item list (`/mapping`) | 1 day |
| Wiki Bucket query results | 1 day |
| Wiki search results | 1 day |
| Game icons (wiki images, RuneLite item icons) | Permanently, as files in the data folder |
| Wiki template expansions | 1 day |
| Wise Old Man's efficiency rates (the same for every account of a type) | 1 day |
| Wiki pages built from other pages (the quest list) | 1 day, as rendered |
| Wiki pages | Until the page changes. A saved page older than a day is checked against the wiki's current revision id (one request covers up to 50 pages) and downloaded again only if it changed. |

Shared data not tied to an account (everything above but the account sources and icons) is kept in the `cache` table, through `cachedEntry` (and `cached`, its value alone) in `server/src/store/cache.ts`: a saved copy is served while it's within its limit, and when the site fails, it's served however old along with the failure (with nothing saved, the failure is passed on). A failure stands for a minute: until then that key isn't asked for again, so a page that reloads often during an outage doesn't wait through the retries each time. A load already under way for the same key is shared. A whole table that takes time to parse (every quest's requirements, the quest list's points) is parsed once per copy kept (`parsedOnce` in `server/src/sources/wiki.ts`, by when the copy was fetched), as the Goals page reloads while you play.

**Whole tables** are fetched once and reused rather than queried per question: every quest's requirements (Quest bucket), the 12 diary pages, the combat achievement list and the item list (`/mapping`). Requirement checks and item lookups then need no wiki requests while the cached copies are fresh.

**Staying within each source's limits** (expected use assumes about 5 accounts, used heavily):

| Source | Published limit | Expected use |
|---|---|---|
| Hiscores | None published | 1 request per account per 15 min |
| Wise Old Man | 20/min, 500/h and 3,000/day per IP, shared with the WOM RuneLite plugin | About 4 requests per account per 15 min, so under 100 an hour |
| TempleOSRS | None published; asks clients to query only what they need | 1 request per account per hour |
| OSRS Wiki API | None found | A few requests per chat question |
| Wiki prices | No explicit limit; asks for bulk requests instead of looping over item ids | At most 1 bulk request per 5 min, plus the item list once a day |

Every request goes through one shared request handler that:
- sends the User-Agent with contact info;
- sends one request at a time per site: Wise Old Man at least 3 seconds apart, the others at least 1 second apart, timed on a clock that only moves forward and including retries;
- pauses Wise Old Man requests when its `RateLimit-Remaining` header runs low, until `RateLimit-Reset`. The headers report whichever window (minute, hour or day) is closest to its limit, so this also covers the WOM plugin's traffic from the same IP;
- retries rate-limit (429) and server (5xx) errors and lost connections up to 3 times, waiting 1, 2, then 4 seconds or as long as `Retry-After` says (in seconds or as a date);
- gives each request 20 seconds, reading the answer included, and doesn't send it again after a timeout (a POST may have arrived), so a hung connection can't hold up every later request to that site;
- never waits more than a minute: a `Retry-After` or a Wise Old Man pause longer than that (its hourly or daily window) fails the request at once, keeping its status, e.g. "too many requests (429). Try again in 20 hours.", instead of holding the queue;
- names the site in every error, e.g. `Wise Old Man: server error (500)`, `Hiscores: no connection`, `OSRS Wiki: no answer within 20 seconds`, and adds the site's own reason when its error answer gives one (Wise Old Man's "Player was updated less than 60 seconds ago"); error answers are read, up to 4 KB, which also frees their connections. A 404 is a separate `NotFoundError`, which sources turn into "isn't on the hiscores" and the like.

It's `createRequester` in `server/src/http/requester.ts`: one promise queue per host, with the clock and `sleep` passed in so tests run instantly.

### What each API offers

Verified against the live APIs on 2026-10-27.

- **Official hiscores (Jagex):** `GET https://secure.runescape.com/m=<table>/index_lite.json?player=<RSN>`
  - Returns `{ name, skills[], activities[] }`. Skills are `{id, name, rank, level, xp}` (25, including Overall and Sailing); activities are `{id, name, rank, score}` (92: bosses, clues, minigames, "Collections Logged"). Unranked entries have `rank: -1`: a skill outside the top two million keeps its real level and XP (checked on 2026-10-28: an account's unranked levels add up to its total level), while an unranked activity's score isn't a count. Unknown player: 404.
  - Tables: `hiscore_oldschool`, `hiscore_oldschool_ironman`, `hiscore_oldschool_hardcore_ironman`, `hiscore_oldschool_ultimate` (plus skiller, fresh start, deadman, seasonal). They nest: every account is on the main table, every iron type is on the ironman table, and a hardcore ironman who died stays on the hardcore table with frozen stats. Telling account types apart means comparing tables.
  - No key, no CORS headers, no published rate limit.
  - In the app (`server/src/sources/hiscores.ts`): `fetchHiscoresText` returns the answer exactly as received, which is what gets stored, but only after checking it parses as hiscores (a maintenance page can arrive with a 200); a 404 becomes "Hiscores: <name> isn't on the hiscores". `fetchHiscores` returns the parsed data, or null for an unknown player. Parsing keeps every skill and activity in the response's order, so a new one appears without a code change. Unranked entries keep `rank: -1`. An unranked skill's level and XP are still used (the combat and total level count them, and the stats tiles show them); only a skill with xp -1 counts as having no level. An unranked activity's score (-1, or 0 for a few newer activities) isn't a count. When an answer doesn't fit, the details go to the server's console. Stats come from the main table, which every account is on.
- **Wise Old Man:** base URL `https://api.wiseoldman.net/v2`
  - `GET /players/:username`: type (regular, ironman, hardcore, ultimate), build, EHP, EHB, time to max, and the latest snapshot (skills, bosses, activities, computed). Also gains for a period or date range (`/gained`), snapshots and timelines, achievements and progress, records, and name changes. `POST /players/:username` updates a player; `POST /players/:username/assert-type` re-checks its type. Players are found by their current name only.
  - `GET /names?username=<name>&status=approved&limit=50` searches name changes by part of a name, matching either the old or the new name, case-insensitively (pages default to 20 results, at most 50). Checked against WOM's documentation on 2026-10-28; it's how a renamed account is found from its old name.
  - Limits per IP: 20/min, 500/h, 3,000/day (an API key from their Discord raises them). Every response has `RateLimit-*` headers, and a 429 has `Retry-After`. They ask for delays between requests, automatic updates no more often than every 1–6 hours, and a User-Agent with contact info (or risk an IP ban).
  - The Wise Old Man RuneLite plugin and RuneLite's built-in XP Updater already update WOM when you log out after gaining XP.
  - In the app (`server/src/sources/wom.ts`): for the kinds that get stored (player, weekly gains, achievements) a text fetcher returns the answer exactly as received after checking it parses (when an answer doesn't fit, the details go to the server's console); a 404 becomes "Wise Old Man: <name> isn't tracked", and `getPlayer` returns null instead. The parse functions are exported so stored answers can be read back. A player type Wise Old Man adds later reads as `unknown`, and a player it has never updated has no boss kills (an unranked boss has kills 0 and rank -1). Gains have no start or end when Wise Old Man has no data for the period; a date range is checked before asking and sent as full ISO times. Name changes come from the name-change search, keeping only approved changes of exactly that name (old or new), newest first. Efficiency rates keep `realRate`: where a method trains two skills, `rate` is this skill's share and `realRate` the XP per hour it really gives. `updatePlayer` (a POST, answered with the updated player) asks Wise Old Man to update a player: on Refresh only when `canRequestUpdate` says the player's data is over an hour old, and never for a player Wise Old Man doesn't track, since an update would start tracking them; starting to track is offered when adding an account. Efficiency rates follow the account type: regular uses `main`, ultimate `ultimate`, every other iron type `ironman`; they're kept a day in the cache (`getCachedRates`), being the same for every account of a type. Hours to a target XP (`hoursToTarget` in `server/src/calc/estimates.ts`) walk a skill's brackets as Wise Old Man's own algorithm does (checked against its `EfficiencyAlgorithm.calculateSkillTime`, 2026-10-28): each method's `rate` holds from its start XP to the next method's, the last runs to 200M, and a method with no rate takes no time (it's trained alongside another skill), though it's still named. They're efficient hours, as its EHP counts them, so a method that trains two skills counts at `rate` rather than its `realRate`. Its data has a slip, a Hunter bracket at 24,886 XP listed after the one at 91,721; Wise Old Man's walk would count that stretch negative and then twice, so a method that starts below the one before it is left out instead. The methods walked are listed in order, a method the walk comes back to named again. `skillRates` finds a skill's rates by its hiscores name (the hiscores' Runecraft is Wise Old Man's `runecrafting`: `womSkill` in shared); Wise Old Man has none for Magic and Hitpoints (nor Fletching for main accounts), which it counts as trained alongside other skills, so such a skill gets one method that takes no time and says so.
- **TempleOSRS:** `https://templeosrs.com/api/...`
  - `collection-log/player_collection_log.php?player=<RSN>&categories=all` returns every logged item with count and date obtained, plus totals, last sync times, EHC and hiscores rank. Items only arrive once synced by the Temple OSRS RuneLite plugin (a sync button in the collection log, plus optional automatic sync of new items without counts). RuneLite's XP Updater can update Temple stats on logout.
  - No published rate limit; they ask clients to query only what they need.
  - In the app (`server/src/sources/temple.ts`): the stored kind (`temple_clog`, fetched at most hourly and on Refresh) is the whole log with item names and the items still missing (`categories=all&includenames=1&includemissingitems=1`), exactly as received; it's compared for changes without the player's rank and last sync time (`comparableLog`), which move without the log changing, so only a changed log adds a snapshot (see Database → `snapshots`). An item counts as obtained when it has a count above 0 or a date, and a missing count reads as unknown rather than failing the whole log (none seen live: all 1,882 items of a full log had either a count and a date or neither). Temple's times are UTC without saying so (checked against `dateformat=unix` on 2026-10-28). A player who has never synced gets Temple's error code 402 (so does an unknown name): the stored kind's fetcher gives a `NotFoundError`, and `parseCollectionLog` reads such an answer as null; any other refusal passes on Temple's message. The log is only ever fetched through the stored kind (at most hourly, or on Refresh), never directly. Each category's tab (bosses, raids, clues, minigames, other) comes from `categories.php`, asked once a day, with Other for a category it doesn't list yet or one in a tab it adds later, and its name from its key (`chambers_of_xeric` is Chambers of Xeric), except twelve the key can't name (apostrophes, capitals, a "The"), which are listed as the wiki's Collection log page names them (`kree_arra` is Kree'arra, `champions_challenge` Champion's Challenge, `hueycoatl` The Hueycoatl; checked against all 125 categories on 2026-10-28). The add-account lookup asks for the summary only (no `categories`), for whether and when the name last synced. The log's schema (`CollectionLogSchema`, with the tabs as `TEMPLE_TABS`) is in shared, for the Collection log page.
- **OSRS Wiki:** `https://oldschool.runescape.wiki/api.php`
  - Search (`action=query&list=search`) and page sections and content (`action=parse`).
  - Structured data through the Bucket extension (`action=bucket&query=bucket('quest').select(...).where(...).run()`), 51 tables including: Quest (requirements with skill levels, "not boostable" and "required to start" flags, the full prerequisite quest tree, and other requirements as text), Combat achievement (id, name, tier, monster), Infobox bonuses (equipment stats), Recommended equipment, Dropsline, Money making guide, and item and monster infoboxes.
  - Content is CC BY-NC-SA 3.0, so answers link the source page.
  - In the app (`server/src/sources/wiki.ts`): every call uses `format=json&formatversion=2`. A refusal passes on the wiki's reason ("OSRS Wiki: Bucket questt does not exist."), and a missing page is a `NotFoundError` ("there's no page called …"). Titles are written as the wiki does (spaces, a capital first letter), so `Dragon_Slayer_II` and `Dragon Slayer II` share a cache entry, and redirects are followed. `searchWiki` gives the top 5 pages with plain-text snippets; `getSections` a page's sections by index; `getSectionText` one section as plain text: a line per heading, paragraph and list item (nested items indented) and `cell | cell` per table row (a list in a cell kept apart with semicolons, a nested one in brackets, so a quest's prerequisite tree stays readable), links as their text, without references, navboxes, the table of contents (which the wiki is also asked not to send), edit or map links, cut at 4,000 characters with "… (truncated; ask for a narrower section)", and with the section's URL. A section index must be the wiki's (`1`, or `T-1` for one taken in from a template), checked before asking. Page parts are cached under `page:<title>:<part>` as the wiki sends them, with the page's revision id; a section's HTML becomes text when it's read, so a better conversion reaches pages already saved. Once a part is a day old, a single `latestRevisions` request (up to 50 titles; it follows the wiki's spellings and redirects) checks it along with every other day-old page: unchanged ones count as checked, and changed ones are marked out of date (left out of later checks) and downloaded again when next asked for. A fetch already under way for the same part is shared. `getPageWikitext` gives a page's wikitext, cached the same way. `bucketQuery` and `expandTemplates` are kept a day. Every cached answer used is reported to the caller (`WikiCtx.noteRead`: when it was fetched, and the failure when it's an old copy), so the AI's tools can say how old their data is and when it's stale.
  - Requirement checks (`server/src/calc/requirements.ts`): every quest's requirements come from one Quest bucket query (`bucket('quest').select('page_name','requirements').limit(2000).run()`, kept a day; `findQuestReqs` finds a quest's by its name as the account or the AI writes it), and each diary's tasks from its page's wikitext (`loadDiaryPage` for one area; `loadDiaryPages` reads the 12 `<area> Diary` pages one after another, so the first read's revision check covers the rest). Skills go by the hiscores' names, which are the wiki's (Runecraft), and a combat level by `COMBAT_LEVEL` ("Combat level"), which an account's levels must include for it to be checked. In a quest's requirements, a line of `data-skill` spans gives skills (a `<sup>` after one says "not boostable", and "required to start" as against "not required to start"), and "Quest points" the quest points. A line with more on it than its levels, their notes and links to their skills (Bucket's reference markers don't count) gives them only when that text just explains them: it's in brackets or starts "to" or "for", and has no word that could make it a condition or a way around the level ("or", "unless", "if", "except", "either", "instead", "otherwise", "optional", "any", "some", "depending", "bypass…", "alternative…", "recommended", "Ironman", "not necessary", "not required"; "47 is recommended" recommends another level, so it isn't one). The text is then the level's `note` (Troll Stronghold's Agility 15, "47 is recommended"; Dragon Slayer I's quest points, "to enter the Champions' Guild"); otherwise the line is kept as plain text and its levels aren't checked (Desert Treasure I's "Slayer 10 or the gas mask", Architectural Alliance's "Mining 42 for any Lovakengj activity"). A line about "the following quests" starts the tree of quests needed, by `*` depth (each line's link), and "Completion of [[X]], which requires the following quests:" puts the list under X. A line of text in the tree is a need of the quest above it ("100 Kudos" under Bone Voyage), and a quest under it goes under that quest too. "Completion of [[X]]" or a lone quest link gives one quest, "None" is skipped, and every other line is kept as plain text. A diary table (`data-diary-tier`) row is a numbered task and its requirements: a line of only `{{SCP|Skill|level}}` templates gives skills (`{{Boostable|no}}` after one that can't be boosted; `{{SCP|Combat|n}}` a combat level; a range such as `29-42` is no level), and so does one whose other text just explains its levels, by the same rule, as their note ("neither boostable" and "only Hitpoints is boostable" also say which can be boosted); a sub-bullet belongs to the line above it (one of several Barrows sets, how to make an item), so it's kept as text; a line of only "Completion of" quests gives quests to finish, "Started" or "Quest start of" quests to have started, "Partial completion of" quests to have partly done, and anything else (items, alternatives, conditions such as "for Ironman accounts") is kept as plain text. Each footnote (`{{efn}}`: an ironman's requirement, a fee) is kept as text of its own, one used again by its name with the text it was first given; notes are left out. Templates are written out (`{{SCP|Attack|link=yes}}` is "Attack", `{{SCP|Quest|32}}` "32 quest points"). A check (`checkQuest`, `checkDiaryTier`) is met when everything that could be checked is; what couldn't (plain-text requirements, a skill the account's levels don't have, a quest not in its quest list, a quest to be partly done that's in progress) is listed as unchecked, a diary's with its task's number. Quest names match ignoring case, how apostrophes are written and the wiki's "(quest)" or "(miniquest)", and Recipe for Disaster's parts match by the wiki's name or the game's ("Recipe for Disaster/Freeing the Goblin generals" is "Recipe for Disaster - Wartface & Bentnoze"). A quest needed is listed once, however many quests need it, and with its own needs (quests and text) only while it isn't finished. A diary tier with no tasks read is a `SourceError` rather than met. Checked against all 233 quests and 492 diary tasks on 2026-10-28. Quest points aren't saved by Character Export, the hiscores or Wise Old Man, so an account's are worked out: `loadQuestPoints` reads each quest's points from the wiki's quest list (`Quests/List`, which the wiki builds from the quests' pages with DPL, so it changes without a revision of its own: `getRenderedPage` asks for it rendered and keeps it a day), the column under the quest point icon in each of its tables (a row whose cell isn't a number is left out; the miniquests' table has no such column). A quest whose parts are listed as quests too (Recipe for Disaster) counts by its parts, which gives the page's own total (184 quests, 343 points on 2026-10-28). `questPointsOf` adds up the points of an account's finished quests, matched by `questKey`; `checkQuest` lists the quest points as unchecked when the account's aren't known.
  - Gear and item info: a boss's recommended gear comes from the Recommended equipment bucket (`bucket('recommended_equipment').select('page_name','page_name_sub','json').where('page_name', <page>)`, the page being e.g. `Vorkath/Strategies`), a row per style (`loadRecommended`, kept a day), its `json` being `{"Recommended Equipment": {"head": [tier, …], …}, "style": "Ranged (crossbow)"}`. `parseRecommended` (`server/src/calc/gear.ts`) reads each slot's tiers, best first, a tier's items being its page links, whatever separates them (` / `, ` + ` for bolts used together, ` > ` for a preference within the tier), without the icons or Bucket's reference markers; what doesn't fit is left out rather than refused. An item whose icon shows another item is a group (God blessing has the Peaceful blessing's icon; 73 such links in 329 of the 498 setups, checked on 2026-10-28); one whose icon is the group's own (a few God blessing links) isn't seen as one. `ownedGroupItems` finds, for each slot, the account's item in each of its groups: one the group's page lists (its links, and the items of its `{{plink}}`, `{{plinkp}}` and `{{CostLine}}` templates; the page kept until it changes, a missing page listing none) that goes in the slot by its stats (`itemStats`; a two-handed weapon fills the weapon or special attack slot; an item the wiki gives no slot for counts), since a page also lists items of other slots (God capes lists god staves). `findUpgrades` lists every slot with the best item of the setup's that the account owns (the setup's name for it, or for a group the account's item in it), and up to 3 items from the tiers above it, best first (from every tier when it owns none), each saying whether it's a group. Owned items match ignoring case and apostrophes (`ownedKey` in `server/src/items/itemNames.ts`), and count whatever state they're in (`(uncharged)`, `(empty)`, `(inactive)`, `(u)`, a number of charges, poisoned `(p)` to `(p++)`), ornamented, locked, trimmed or heraldic (`(or)`, `(l)`, `(t)`, `(g)`, `(c)`, `(h1)`…) or worn (Barrows' `Karil's coif 75`); a version such as `(i)`, `(e)` or `(f)` is another item. Items priced over a budget are left out, unpriced ones stay, and an item is buyable only when the account can trade (every type but regular can't) and it has a price; otherwise its price is only for reference. `getItemInfo` (`server/src/services/itemInfo.ts`) gives each named item's stats, price, the time of the trade it's from (a rarely traded item's can be months old), buy limit, members flag, up to 5 drop sources, whether anything knows it by that name (`found`), and why a part is missing (`errors`: a source's failure, while it can't be reached with nothing saved; the other parts stay). A name is taken as the item list's when it's one of its items' names but for case (Yellowfin isn't Yellow fin), else but for case, apostrophes and spaces (`itemFinder`); otherwise the name asked for is looked up as the wiki writes names (a capital first letter), with no price, limit or members flag (the Grand Exchange doesn't trade it), and takes the wiki's name for it from its stats' page or its drops (Bucket matches names whatever their case), since a looser match can be another item (Dragon defender ornament kit for Dragon defender, Anti-venom(4) for Anti-venom+(4)). The price is the latest instant-buy price, else the instant-sell price (`latestTrade` in `server/src/sources/prices.ts`, which the bank's prices use too); the latest prices are fetched while the wiki is asked, since they come from another site. Stats come from the Infobox bonuses bucket (`itemStats` in `server/src/items/itemStats.ts`, kept a day), its fields named (Bucket can't select `*`): the page's row for the item, or the page's first row when none is named for it, else the version's row on its item's page (Black mask (10) is `Black mask#(10)` on Black mask). Drop sources come from the Dropsline bucket (`where('item_name', …)` with a limit of 5,000 rows: the wiki gives 500 without one, and coins have over 2,000), each row's `drop_json` giving `Dropped from` (`Vorkath#Post-quest` is written `Vorkath (Post-quest)`), `Rarity` and `Drop Quantity`. They're ranked by chance, a rarity word counting as a chance among the fractions (Always 1, Common 1/16, Uncommon 1/64, Rare 1/512, Very rare 1/5,000, anything else last) and equal chances keeping the wiki's order; a row that can't be read is left out. `bucketSelect` writes a Bucket query with its names and values quoted (`'Karil\'s coif'`).
- **OSRS Wiki prices:** v2 at `https://prices.runescape.wiki/api/v2/osrs/` (v1 still works but may be removed). `/latest` (all items, about 340 KB, or one item with `?id=`), `/mapping` (names, ids, GE limits, alch values; about 870 KB), `/5m` and `/1h` (averages can have two decimals), and `/timeseries?id=&lookback=` with `24h`, `7d`, `6m` or `1y`. Prices can exceed 2,147,483,647 (the 3rd Age pickaxe traded at 8,865,000,000 on 2026-10-28), so they're never held as 32-bit integers.
  - In the app (`server/src/sources/prices.ts`): `getMapping` gives every tradeable item (asked once a day; a buy limit, alch value or value the wiki leaves out reads as null; about 500 items have no limit and 19 no value), and `getLatestPrices` every item's latest high and low with when each trade happened (asked once every 5 minutes; null where there's been no such trade, and no entry for an item never traded; a last trade can be months old, which whatever shows the price says). Both are cached as the API's JSON numbers, which hold every price exactly (to 2^53).
- **Both wiki APIs reject generic User-Agents** (a `python-requests` one got 403), so every request sends a descriptive User-Agent with contact info.
- **WikiSync** (not used for now): `https://sync.runescape.wiki/runelite/player/<RSN>/STANDARD` returns quests, diaries with per-task detail, combat achievement ids, collection log item ids, levels and music tracks. Anyone can read it by name, and it needs the WikiSync plugin.

## RuneLite data (Character Export)

The hiscores don't include quests, achievement diaries, combat achievements, bank, inventory or worn gear. These come from [Character Export](https://github.com/DZWNK/Character-Export), a Plugin Hub plugin (installed the normal way; BSD 2-Clause) that writes JSON files per account to `.runelite/character-exporter/<Character Name>/`. It has no network code. The backend reads the files from the RuneLite folder: `~/.runelite` on every OS, or `/mnt/c/Users/<user>/.runelite` when the app runs in WSL and RuneLite runs on Windows.

| File | Updated when | Contents |
|---|---|---|
| `character.json` | Login, stat change | Skills (level, boosted level, XP), world, player name |
| `quests.json` | Login, quest change | Every quest's state (not started / in progress / finished) |
| `diaries.json` | Login, change, diary journal opened | 12 areas × 4 tiers: completion, tasks done, named tasks |
| `combat_achievements.json` | Login, change | Every combat achievement task by name with completion, by tier |
| `collection_log.json` | A collection log entry is viewed | Items from the entries viewed so far |
| `bank.json` / `seed_vault.json` | Bank / seed vault opened | Full contents with item names |
| `inventory.json` / `equipment.json` | They change, or Sync Available is pressed in the plugin's side panel | Carried / worn items |

- **Formats** (checked against real files, v0.6.0): `stats` keyed by skill name; quest `state` is `FINISHED`, `IN_PROGRESS` or `NOT_STARTED`; diary and combat achievement tiers are keyed in lowercase (`easy` … `grandmaster`); container files list `items` with `slot`, `id`, `quantity`, `name`; `exported_at` carries a UTC offset and up to 9 fractional digits. Full field list in `PLAN.md` → Task 17.
- **Gaps:** named diary tasks need each area's diary journal opened once (completion and task counts are always there). Later exports can drop those names (seen after re-logging: only Karamja kept them), so the app keeps, per area and tier, the most recent names it has seen in its snapshots, shows when they're from, and flags them as stale once the tier's task count has changed since; reopening that journal refreshes them. The plugin's own `complete` flag for a tier can contradict its tasks (seen for Karamja: the easy tier with all 10 tasks done but not complete, the medium tier with 4 of 19 done but complete), so a tier counts as done when all its named tasks are done while the names are current, and by the flag only when the names are missing or stale (an empty task list counts as missing). `seed_vault.json` uses the bank's format (from the plugin's source; not yet seen on a real account). The collection log only covers entries opened in game, so the app takes the collection log from TempleOSRS instead and ignores `collection_log.json`. The bank and seed vault are only as fresh as the last time they were opened. The plugin also limits how often it saves each file (the inventory at most every 5 seconds; worn gear, the bank, the seed vault and the character file every second; quests, diaries and combat achievements every 5 seconds) and drops a change that comes sooner rather than saving it later (checked in its source, 2026-10-28), so after a quick run of changes a file stays behind until the next change after that wait, or until Sync Available in its side panel saves everything at once. Equipping an item straight after moving it in the inventory can leave the item both worn and in the inventory, as the files have it.
- **When the files are read:** a setting, changed in the app's settings page and stored in its database, picks the mode:
  - **Automatic:** while an account is open in the browser, the page asks the server to check every few seconds (interval configurable), so the dashboard updates as you play. Nothing runs when no page is open.
  - **Manual:** files are only read when you press Refresh (and once when the account is added, so its first page has them).

  In both modes, a chat message checks the files before the AI reads account data, so answers never use older data than what's on disk (the AI may see newer data than the dashboard until you refresh). Every check compares modified times and re-reads only files that changed; there are no file watchers. The Refresh button exists in both modes. The setting covers Character Export's local files only; the check itself asks no site, so online sources aren't polled this way (rate limits). A page it reloads fetches what it shows when that's past its freshness limit, as when opened (the Overview and Goals: the hiscores, Temple's log), so while you play with one open the hiscores are asked at most every 15 minutes and Temple hourly, as the limits above expect.
- **Reading the files:** the plugin overwrites files in place, so a read can catch one half-written: retry when JSON fails to parse. The format belongs to a third party (reviewed at v0.6.0, commit `0386dcc`), so store raw file contents in snapshots and parse defensively.
- **In the app** (`server/src/sources/characterExport.ts`): `findAccountFolder` finds an account's folder in `<RUNELITE_DIR>/character-exporter/` by nameKey (so a folder written with a non-breaking space matches), taking the one written to last when two match (a rename that only changed separators). `checkFiles` compares each file's modified time with the one saved and reads only those that changed. A file that isn't JSON yet, or that RuneLite has open, is read again 250 ms later, 3 tries in all; one still unreadable, or not in the expected format (the schemas in `characterExport.schemas.ts` check only what the app reads and keep any other fields), is noted as failed with the data from before kept (and remembered while the server runs, since a file that has never read has no data to note it on, until it reads or the account's folder is gone), and is tried again at the next check. The files are looked at together, and what changed is saved in order. `exportFiles` gives what the app has of each of an account's files (the saved copy, when Character Export saved it, why the latest read failed, and what to do in game, or nothing for a file the account's type doesn't have, such as an ultimate ironman's bank); the Overview and the Bank and gear page both read the files through it. A RuneLite folder that can't be read is reported for every kind, and as a problem in the add-account lookup, rather than failing the check. A check of an account already under way is shared, so two can't save over each other. A good file is saved exactly as read, dated by its modified time; a rewrite that only moved `exported_at`, `reason` or `session_id` on isn't a change, so it adds no snapshot. Each check reports the kinds that changed, the kinds with no file yet (every kind when the account has no folder) and the kinds that failed; `MISSING_FIX` says what to do in game for each missing one ("Open your bank in game so Character Export saves it."). `mergeDiaryNames` gives each diary tier the task names of the latest file, or of the most recent earlier snapshot that has them, with when they're from, flagged as stale once their completed count no longer matches the tier's; `savedDiaries` gives an account's that way (the Overview and the account's data read them through it), and `mergeDiaryHistory` merges every file of a history the same way in one pass (This week's diary tiers done). `readSnapshots` reads snapshots back with a file's schema. On the page (`client/src/data/useFileCheck.ts`), an open account in Automatic mode is checked at once, then every `pollSeconds` while the page is visible and as soon as it's shown again, and the pages that read a file that changed reload: the Overview for its files, Bank and gear (with its search) for the bank, seed vault, inventory and gear, This week for the quests, diaries and combat achievements, and Goals for every file. Only Goals reads `character.json`, which changes with every stat while playing (skill goals' XP), and the Collection log reads no file. Refresh reads the files in either mode.
- **If it breaks or is abandoned:** take it over as our own plugin (about 3,500 lines, BSD 2-Clause), or use Bank Bridge for bank, inventory and gear.
- **Alternatives considered:**
  - OSRS Companion (the original choice) writes no local files; it uploads everything to a third-party website.
  - WikiSync covers quests, diaries, combat achievements and the collection log, but makes them public by name and has no bank.
  - Persistent Bank was disabled on the Plugin Hub as unmaintained.
  - Bank Bridge serves data over a local WebSocket only while RuneLite runs, and only knows whole diary and combat achievement tiers.
  - Our own plugin: RuneLite only loads plugins that aren't on the Plugin Hub in developer mode, which is off whenever a launcher starts the client, so it would mean playing on a developer build or publishing it.

## Database

| Table | Holds |
|---|---|
| `accounts` | Name as shown in game, a matching key, account type (and whether it came from Wise Old Man or was set by hand), notes, when it was added |
| `source_state` | The latest data per account and data type (hiscores, WOM player, WOM weekly gains, Temple collection log, each Character Export file, ...): raw data, a content hash, when it was fetched, and the file's modified time for Character Export. Reads and freshness limits use this table. A fetch that brings the same data still moves `fetched_at` on; a successful fetch clears any error; a failed one keeps the last good data and notes the error and when (a source never fetched has nothing to note). |
| `snapshots` | History: a copy is added whenever the data changed (see retention below). Whether it changed is decided by a SHA-256, inside one transaction with the save: of the data, or of a text the source gives to compare, so what moves without the data changing (Character Export's export time and reason, which change on every write; Temple's rank and last sync time) doesn't count as a change. A file's snapshot is dated by when the file was written, not when the app read it. |
| `cache` | Shared data not tied to an account: wiki pages (with revision id), Bucket results, search results, GE prices, the item list, Wise Old Man's efficiency rates |
| `goals` | Account, title, kind, target (JSON), status (active, done, dropped), position in the user's order, created, completed and dropped times (details in Goals) |
| `chat_sessions`, `chat_messages` | Conversations per account, stored in a provider-neutral format (details in AI layer) |
| `settings` | Settings changed in the app (RuneLite update mode and interval, time zone, ...), one row per setting with its value as JSON; a saved value that's no longer valid, or a key that's gone, falls back to the default. Secrets and paths stay in `.env`. |

**History retention:**
- Stats and progress (hiscores, Wise Old Man player, Temple collection log, quests, diaries, combat achievements): every change.
- Bank and seed vault: at most one per day (the day's last version), enough for a bank value chart.
- The character file (levels and XP from Character Export): every change, for the full levels and XP history, though the plugin rewrites it every few seconds while you play (a rewrite that only moves its export time on isn't a change).
- Inventory and worn gear: latest only; they change constantly while playing.
- Wise Old Man gains and achievements: latest only; Wise Old Man keeps that history.

**Conventions:**
- **Names** match ignoring case, with spaces, underscores, hyphens and non-breaking spaces treated as the same (Wise Old Man's rule). A name sent to the app must be an OSRS name: 1 to 12 letters, numbers, spaces, hyphens or underscores (a pasted non-breaking space counts as a space). The matching key is also how the app finds each account's Character Export folder. A renamed account is updated in the app and keeps its history.
- **Times** are stored as ISO 8601 text in UTC and always shown in the configured time zone. The time zone setting is either Automatic (the browser's time zone, which the page reports to the server) or a zone picked from a list. Day-based rules, such as one bank snapshot per day, use that zone, and the AI is given the current local date, time and zone. A day starts at its midnight there, or, where the clocks jump forward at midnight (Chile, Cuba), when they land at 1 AM. A saved zone this browser or server doesn't know (picked in another browser, say) counts as UTC rather than breaking the settings. Times are written in US English, like the rest of the interface (Oct 27, 2026, 5:00 PM); recent ones read "just now", "5 minutes ago", "3 hours ago", then by calendar day "yesterday" and "3 days ago", and after a week the date.
- **Deleting an account** deletes all its data, after confirmation. Foreign keys are on.
- **The file** is `wise-old-model.db` in the data folder. If it can't be opened (or migrated), the server stops with the reason.
- **Migrations** run automatically at startup; they live in code (`server/src/db/migrations.ts`) and run in name order. All pending migrations run as one transaction (`BEGIN IMMEDIATE`, which also keeps a second process out), so one that fails partway leaves nothing behind. Foreign keys are off while they run, as SQLite's guide to changing a table requires (otherwise rebuilding a table deletes every row pointing at it), and a foreign key check runs before committing; a migration that would leave rows pointing at missing rows is undone. A clock that went backwards between migrations doesn't block startup.
- **Write-ahead logging** is on (safe because the database lives on a local drive), with `synchronous = NORMAL`, SQLite's recommended setting for it: a save doesn't wait for the disk (about 7 ms a save otherwise, several times a minute while playing), which can't corrupt the file, and a power cut can lose only the last few saves, which the next file check or fetch makes again. A write waits up to 5 seconds for a lock instead of failing at once.
- **Backups** are automatic: at startup when the newest backup is over a day old, and always right before a migration runs on an existing database. Each is a full copy made with SQLite's `VACUUM INTO` (safe while the app runs) into `backups/` in the data folder, named by UTC time without colons so Windows accepts it (`wom-2026-10-27T120000Z.db`); the newest 7 are kept. A backup named in the future (made while the clock was ahead) doesn't count as the newest. If the daily backup can't be made, the server warns and starts anyway; an old backup that can't be deleted (Windows refuses while another program has it open) is tried again next time. The backup before a migration must succeed, or nothing is migrated. Settings → About shows the newest backup and has Back up now (`POST /api/backups`); a second backup in the same second is the first one.

## Goals

Goals belong to one account. Progress is computed from the account's data, never stored.

| Kind | Target | Progress shown |
|---|---|---|
| Skill | A level or an XP amount | Progress bar, XP to go, hours at Wise Old Man's efficient rates |
| Quest | Complete a quest | What's still needed, from the same requirement check the AI uses |
| Diary | Complete an area's tier | What's still needed |
| Combat achievements | A task, or a whole tier | Done or not; points toward the tier |
| Boss kills | A kill count | Current kill count |
| Collection log | An item, or a whole entry | Obtained or not; items in the entry |
| Item | Own an item | Where it is, from bank, inventory and gear |
| Custom | Free text | None; ticked off by hand |

- **Completing:** a goal completes itself when the data shows it reached; it moves to Done with the date and appears in This week. It can be reopened. Custom goals are ticked off by hand.
- **Dropping:** a dropped goal is hidden but kept.
- **Order:** active goals are in the user's order (drag to reorder). The AI reads that order as priorities for "what should I work on next?"
- **The AI:** it can suggest goals and add or update them, each after the user approves (e.g. offering 75 Magic and Dream Mentor as goals after "Can I do Dragon Slayer II?").
- **Page:** Add goal and Suggest goals buttons; active goals with progress (quest and diary goals list what's still needed, with an "Ask the AI for a plan" link); a Done list with dates. Suggest goals posts a request into the chat ("Suggest a few goals for <account> based on my progress and current goals"); each suggestion the AI adds comes up as Approve / Decline.
- No target dates (left out to keep goals simple).
- **The page, built** (`client/src/pages/Goals/`, data from `GET /api/accounts/:id/goals`; queries and changes in `client/src/api/goals.ts`):
  - **Header:** Add goal and Suggest goals. Suggest goals sends "Suggest a few goals for <account> based on my progress and current goals." to the account's chat, with "From Suggest goals" under it, and each quest or diary goal's "Ask the AI for a plan" sends "Make me a plan for this goal: <goal title>." with "From Goals" (through the chat's context, `useChatAsk`). Sending one closes the page panel on a narrow window, so the answer shows. While the chat loads or answers, and outside a chat (a page shown on its own), both are marked disabled (`aria-disabled`, so the tooltip, "The chat is still loading.", "The chat is answering. Wait for it, or press Stop." or "Available once the chat is set up", still shows on hover, and screen readers read it as its description) and do nothing.
  - **Active goals** are in the user's order. Each has a drag handle, its icon (the skill's, boss's or item's, or its kind's), its title and kind, and a bar for a skill or combat achievement goal (rounded, held below 100% until reached). Below come what the server says of it, and "Still needed" with a red dot (not met) or a yellow one (under way), worded for screen readers. A custom goal has a box to tick it off (ticked only while that's being saved), and every goal has Drop, which offers Undo. When every goal is done, the page says no goals are active.
  - **Moving:** a goal is moved by dragging it onto another's place (a drag that ends elsewhere is forgotten), or with Alt+↑ and Alt+↓ on its handle, which keeps the focus (React gives it back when the row moves) and says where it went ("Reach 75 Magic moved to 1 of 5."). The new order shows at once and is saved with the reorder route; the page reloads only if the server refuses it.
  - **Done** lists titles and dates, newest first, each with Reopen. Dropped goals aren't shown. A change the server refuses says why. Failures of the hiscores or Temple's log are said above the goals, and the page has Refresh.
  - **Add goal** is a modal dialog. It offers the eight kinds, each with its fields: a skill and a level or XP amount; a quest; a diary area and tier; a whole combat achievement tier or one task; a boss and its kills; a collection log item or a whole entry; an item; or a custom goal's title. Names aren't typed but picked from the account's lists (`GET /api/accounts/:id/goals/options`, from its saved data): the skill from a dropdown of its skills in the stats tab's order, the rest from searchable dropdowns (`SearchSelect`, the ARIA combobox pattern with list autocomplete and automatic selection: typed words narrow the list in any order, ignoring case and apostrophes, an exact name first, then names starting with what's typed, 50 at a time; the first match is the one Enter picks, ↑ and ↓ move from it, keeping it in view and naming it to screen readers, a status line says how many match to screen readers, a click picks, and Escape closes the list before the dialog; the list floats over the dialog like a native dropdown, placed under the box or above it when there's more room there, following it when anything scrolls, and fixed from its first render, so opening it never resizes the dialog or moves the box from under it). The lists leave out the quests finished, the combat achievement tasks done, the collection log items obtained (each item once, with an entry it's in) and the entries completed; bosses are the hiscores' activities Wise Old Man's boss list names (all of them without one). A list whose data isn't saved says what to do instead (and combat achievement tasks Character Export hasn't named say so), an empty one says why ("Every quest is finished."), the fields say when the lists are loading or couldn't be had, and a name that isn't picked isn't sent ("Pick a quest from the list."). An item is typed, as the game has too many to list. The title field shows the title made from the target. What's asked is checked with the shared schema first, so a custom goal without a title costs no request, and a refusal from the server is shown in the dialog.
  - **Reloads:** a change reloads the page and This week, which lists goals done. The file check reloads the page when any Character Export file changes, and with This week when it completed goals. The page and This week say a source's failure the same way (`failureNotes` in `client/src/components/sourceNotes.ts`: "The hiscores: fetched 2 hours ago. The last try failed: …").
- **Built** (`server/src/goals/`, schemas in `shared/src/goals.ts`): a target is a skill level (2 to 126) or XP amount, with the XP it started from; a quest; a diary area and tier; a combat achievement task or tier; a boss's kill count (a hiscores activity that Wise Old Man's boss list doesn't name is refused when the list is saved); a collection log item or entry; an item to own; or custom, which is its title. A goal is titled from its target unless given a title (`goalTitle`: "Reach 75 Magic", "Complete Dragon Slayer II", "Complete the Ardougne Hard diary", "Elite combat achievements", "500 Vorkath kills", "Get Vorki", "Complete the Vorkath collection log").
  - **The account's data** comes from `loadAccountData` (`server/src/services/accountData.ts`), which the AI's tools use too. It reads only what's saved, so it asks no site. A skill comes from whichever of the hiscores and Character Export's character file has more XP for it (the newer). It also gives quests, quest points, diaries, combat achievements, the hiscores' activities (an unranked one has no count), Temple's log, and what's owned (bank, seed vault, inventory and worn gear, with the places not saved yet; an ultimate ironman's bank isn't one). A part not saved is null, so progress says what's missing and how to get it.
  - **Progress** (`goalProgress`, from that data and the wiki's):
    - **Skill:** a bar from its start XP to the target, and "Level 71. 360k XP to go, about 6 hours at efficient rates." XP is exact under 10,000, then in thousands, then millions; under an hour says so. A skill Wise Old Man counts no time for says that instead. Without rates there are no hours, and it says why they couldn't be had.
    - **Quest or diary:** what's still needed, from the AI's checks: levels short ("75 Magic (you have 71)"), quest points short, and quests not done (red, or yellow when under way; a diary's "(started)" or "(partly done)"). It says how many requirements are left to check on the wiki, or that everything that can be checked is met. A diary tier also counts its tasks done.
    - **Combat achievements:** a task is done or not. A tier is reached when the game says so (Character Export's flag, which follows points), with a bar of the points toward it ("73% of the points needed.", from the wiki's thresholds).
    - **Kill count:** the hiscores' kills toward the target.
    - **Collection log:** an item is obtained or not, with its entry's kill count ("Not yet. 412 Vorkath kills so far."); an entry counts its items.
    - **Item:** where it's owned, in any state (`ownedKey`), or that it isn't, naming the places not saved yet ("Not owned, as far as the app knows: the bank isn't saved yet.").
    - **Custom:** "Tick it off yourself."
    - Names match ignoring case, apostrophes and spaces; quests match by `questKey`.
  - **The shared data** a goal's progress reads is loaded only for the active goals that read it (`SharedData`, kept a day): every quest's requirements and the account's quest points (from the wiki's quest list) for a quest goal, each diary goal's page, the combat achievement thresholds for a tier goal, and Wise Old Man's rates for a skill goal. A part that can't be had is left out, and the goal says why.
  - **Completion:** `syncGoalCompletion` marks active goals the data shows reached as done, dated then. It runs after Refresh, after a file check that read a changed file (which then says how many goals it completed, so the page reloads Goals and This week), and before the Goals page is shown. It reads only what's saved, as nothing done needs shared data, so the file check never makes it ask a site. It marks each goal once, however many syncs run at once, and reads nothing when the only active goals are custom.
  - **Adding:** a goal's names are checked against the account's data where it's saved and written as the data writes them. A name the data doesn't have is a 400, and a goal already reached a 409. A skill goal starts from the skill's XP now, and is refused (409) while the levels aren't known. A new goal goes last. A quest goal whose quest points couldn't be had says why.
  - **Changing:** a goal can be renamed, ticked off by hand (dated now), or reopened (last in the order; refused while the data shows it reached). It can be dropped (kept, hidden, and no longer dated done) or moved within the active goals. A change that's refused saves none of itself. Reordering lists the active goals by id. Any left out follow in their order, one just completed is passed over, and another account's is a 400.
  - **The list:** active goals in order, then done ones newest first, then dropped ones most recently dropped first. Only active goals have progress.

## AI layer

- The LLM sits behind a provider interface so the provider can be swapped.
- **Claude runs through the [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)** (`@anthropic-ai/claude-agent-sdk`), which runs Claude Code inside the app, so usage can bill to the user's Claude Max plan. A billing setting picks the credential: **Plan** (default; Claude Code's own sign-in, and `ANTHROPIC_API_KEY` is removed from the Claude Code process's environment) or **API key** (pay per use, with an optional spending cap).
  - Anthropic's Claude Code legal page: "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code and the Agent SDK." It forbids apps offering Claude.ai sign-in, routing other people's requests through plan credentials, and collecting, storing or intermediating Claude.ai credentials or session tokens. So the app never reads, copies or stores the Claude sign-in; Claude Code handles it (`claude` → `/login`, once per machine).
  - The SDK installs a per-OS Claude Code binary as an optional dependency, like Vite's build tools.
- **Provider interface:** one user turn at a time (a message in; streamed text, tool activity and usage out). The provider runs the tool loop. Tools are defined once in a provider-neutral form (name, description, Zod input schema, handler, read-only flag).
- **Agent SDK setup:**
  - Our tools are an in-process MCP server (`createSdkMcpServer`), with schemas always loaded (`alwaysLoad`) instead of deferred to tool search. None is pre-approved with `allowedTools`: an entry there skips `canUseTool` (the SDK warns `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` when both are set), so every call goes through `canUseTool`, which runs our lookups unasked.
  - `tools: []` removes every built-in tool (no files, shell or web). A custom `systemPrompt` replaces Claude Code's. `settingSources: []` keeps the user's Claude Code settings, `CLAUDE.md`, plugins, hooks and skills out.
  - `cwd` is a folder in the data directory, so these sessions stay out of the user's coding projects. Each chat stores its Claude session id and resumes it on the next message (`resume`); Claude Code compacts long chats itself.
- **Defaults:** Claude Code's `opus` alias (its latest Opus, so the default moves on with new releases; Opus 5.5 today), effort `medium`, at most 20 tool rounds per question (`maxTurns`). All three are settings. The models and effort levels offered aren't written into the app: Claude Code lists the ones the sign-in (or key) can use, each with the effort levels it takes, so new models and levels appear as Claude Code ships them. The model setting is any name Claude Code takes (an alias or a model's id), and the effort any level a model lists.
- **Streaming:** text deltas (`includePartialMessages`) reach the browser over SSE; tool calls show as status lines ("Checking your quests…", "Reading wiki: Dragon Slayer II"); Stop cancels the turn.
- **Writes need approval:** tools that change data (adding or completing goals) use the SDK's `always_ask` permission policy (so an allow rule from elsewhere, such as managed settings, can't skip the question), and `canUseTool` relays the request to the chat as Approve / Decline. Read-only tools are marked `readOnlyHint` so they can run in parallel.
- **Sources:** the server records every wiki page a tool returned during the turn and lists them under the answer, in addition to links the model writes.
- **Context:** one chat per account. The account's name and type are in the system prompt; each message carries the local date, time and time zone.
- **Stored:** chats and messages as shown in the UI (messages, answers, tool activity, sources, usage: tokens on the plan, plus cost with an API key). Claude Code keeps its own transcript for the model's context.
- **Built** (`server/src/ai/`): the provider interface (`provider.ts`: `ToolDef`, `TurnInput`, `ProviderEvent`, `ChatProvider`), a scripted provider for tests (`fakeProvider.ts`) and the chat service (`chatService.ts`). Before each turn the service checks the account's Character Export files as the files check does (`checkFilesAndGoals` in `goalsService.ts`, in either update mode), marking the goals they complete, so the answer sees the game as it is; when a file changed, the turn starts with a `files` event (the files that changed and how many goals that completed), so the page reloads what reads them. A check that fails is logged, and the chat answers anyway. The turn reaches the page as `ChatEvent`s (`shared/src/chat.ts`, which also writes and reads the stream: `formatSse`, `parseSse`): text; each lookup with its status line, the tool's `label` once its input fits the tool's schema ("Looking something up…" otherwise); each change waiting for Approve or Decline, and its answer; then, as the turn ends, the wiki pages the tools noted (each once), the tokens used (input, output and cache reads; the cost only with an API key) and `done` with the stored answer's id. A provider's error comes with what to do when the provider knows it (the Claude provider's about signing in get the `claude` and `/login` steps; with API key billing, a check of the key); a provider failing outright gives its message. Stop ends the answer at once, even while the provider waits on something; closing the page does the same, and so does deleting the chat or its account, which waits for the answer to be stored. However the turn ends, what it left open is settled on the page as in the stored answer: a change still waiting is declined, a lookup still running is marked failed, and a provider that didn't finish is closed. The answer is stored with its error and whether it was stopped; each of its parts but the text has a default, so an answer stored before a part was added still reads. A chat answers one message at a time. A chat is named by its first message (on one line, cut to 60 characters) unless it was renamed first; New chat opens the account's empty chat when it has one, and Earlier chats lists only chats with messages. The chat service's `listModels` gives the provider's models for the billing set, kept an hour per billing and shared by the requests that want them meanwhile (a failure isn't kept); the Claude provider's `models` starts Claude Code as a turn would, asks it `supportedModels()` with no prompt sent (so nothing is billed), and closes it, giving up after 30 seconds. Claude is the provider (`claudeProvider.ts`, built in `main.ts` with the Agent SDK's `query` and passed to `startServer`; it makes its working folder, `<dataDir>/claude/`, when it first starts Claude Code); an app made without one (tests) answers that the AI isn't set up. Per turn it calls `query` with the system prompt, `tools: []`, `settingSources: []`, `includePartialMessages`, the model, effort and most tool rounds from the settings, the working folder, `resume` with the chat's Claude session when it has one, and an `abortController` aborted by Stop or when the turn ends early. Each tool is an MCP tool on the in-process `osrs` server (`alwaysLoad`), its result sent as JSON text and a failure as an error result with its message, marked `readOnlyHint` or `destructiveHint`; `strictMcpConfig` keeps every other MCP server out (the user's claude.ai connectors, plugins, `.mcp.json`), and nothing is pre-approved, so Claude Code asks `canUseTool` before each call (the tools that change data also carry `always_ask`): it runs a lookup unasked, and for a change it makes the tool's summary (a goal that can't be added is refused with why, unasked), relays it to the chat's Approve row, and allows the call unchanged or refuses it ("The user declined this change."); any other tool, or one of the same name from another server, is refused. With Plan billing `ANTHROPIC_API_KEY` is taken out of Claude Code's environment (in any case, as Windows doesn't mind it), and a turn whose Claude Code reports it would still bill an API key (its `apiKeySource` anything but `none` or `oauth`: a Console sign-in, a key helper) stops before asking Claude, saying so; with API key billing the key from `.env` is put in, with `CLAUDE_CODE_PROMPT_CACHE_TTL=1h` and, when set, the spending cap as `maxBudgetUsd` (without a key in `.env`, the answer says so and Claude Code isn't started). Its messages become the chat's events: the session id from `system`/`init`, text deltas from the stream (each text block after the first starting a new paragraph, so one tool round's text doesn't run into the next; a message whose text didn't stream gives it whole), each `tool_use` (named without the `mcp__osrs__` prefix) and its `tool_result`, and the result's usage (input, output and cache-read tokens, cost) with its errors: Claude Code's own, or what the limit reached means ("It used the most tool rounds allowed for one question (20). Ask it to go on, or raise the limit in Settings."), and a result marked as an error (such as "Not logged in · Please run /login") gives its text; the error Claude Code then exits with adds nothing (one error per answer), while a failure before any result (it can't be started, or isn't signed in) is the answer's error, with what to do as for a result's, and a stopped turn's failure adds nothing.
- The model gets account and game knowledge only through tools. Calculations (XP remaining, time estimates, requirement checks, costs) happen in code; the model only interprets the results.
- **Privacy:** everything a tool returns (account names, stats, bank contents) is sent to the AI provider. That's accepted for this project, but nothing else from the machine is sent.

### Instructions

The system prompt (stable for the whole chat, so Claude's prompt cache holds; the Agent SDK caches prompts automatically) tells the model:

1. **Role:** an Old School RuneScape advisor for one account: its name, its type, and that it's the user's own account.
2. **Facts about the account come from tools.** Never guess stats, quests, bank or gear. When data is missing or stale, say so and say how to fix it ("open your bank in game so Character Export saves it").
3. **Respect the account type:** ironmen can't trade or use the Grand Exchange, group ironmen trade only within their group, ultimate ironmen have no bank, and hardcore ironmen get risk warnings for dangerous content.
4. **Numbers come from the calculation tools** (XP, time estimates, requirements, costs), not mental math.
5. **Always check the wiki:** every specific game fact (requirements, stats, drop rates, locations, methods, XP rates) comes from a wiki page read in this chat and is cited. General strategy can come from the model's own knowledge, but the concrete claims behind it are looked up. Every lookup goes through the app's cache.
6. **Ask before guessing** when a request is ambiguous ("best gear upgrade" for which boss or style?).
7. **Decline** botting, macros, real-world trading, account selling or sharing, bug abuse and unapproved third-party clients.
8. **Style:** practical and concise, answer first, lists for steps, times in the user's time zone.
9. **Goals:** it may suggest goals and add them only after the user approves.

Built as `buildSystemPrompt` (`server/src/ai/instructions.ts`): the nine rules as plain prose, the account type's rule spelled out for that type (an ironman can't trade or use the Grand Exchange, so items are obtained rather than bought and prices are for reference; an ultimate ironman also has no bank, keeping items in its inventory, worn gear, seed vault, looting bag and house, and is asked to open its seed vault rather than a bank when data is missing; group ironmen trade only within their group; hardcore types are warned of the risk in dangerous content such as bosses, raids and the Wilderness, checking the wiki whether a death there is safe), naming the tools the numbers come from (`calc_xp`, the requirement checks, `find_gear_upgrades`, `get_prices`) and the goal tools that need approval. It holds no date or time and is the same every turn, so the prompt cache holds it. Each message goes to the provider headed by the local time in the settings' zone with its offset from UTC (the game's resets are in UTC), `Local time: Tuesday 27 October 2026, 17:00 (America/Chicago, GMT-05:00)`, then a blank line (`composeMessage`).

**Rules for every tool:** small, filtered results (never a whole bank or a whole wiki page); an "as of" time on every result; say when data is missing or stale; loose item-name matching ("dragon scim" finds Dragon scimitar): `createItemIndex` in `server/src/items/itemIndex.ts` ranks the exact name first, then names whose words start with the query's words in order, then names containing the query, ignoring case and apostrophes, with shorter names first among equals. `get_item_info` takes only an item's name (ignoring case, then apostrophes and spaces too), since a looser match can be another item. Everything a tool returns is sent to the AI provider.

**Built** (`server/src/ai/tools/`, `buildTools` in `index.ts`, the twenty tools in the order above): each is made with `defineTool` (`define.ts`), which checks the input against the tool's Zod schema before it runs (and before its status line or Approve summary is made), so any provider's tool loop can hand it anything, and refuses a result over 8,000 characters of JSON with an error asking for less (a filter, a search or one section) rather than sending it. Every result has `asOf`, the time of the answer (`defineTool` adds it), with when each source was fetched or saved where it matters (`sources`, `fetchedAt`, `savedAt`, `bankSeenAt`); `stale` lists the sources whose last fetch failed or that don't know the name, so what's given is the last good copy (a wiki or prices answer given from an old copy counts too, through the wiki context's `noteRead`); `missing` lists the Character Export files not saved yet, with what to do in game, and a file whose latest read failed is stale instead (what's given is the read before). A source that fails never fails the tool while there's a copy to give. The account's data comes from the same services as the pages: the overview from `getOverview` (every skill, with levels from the hiscores or the character file, whichever is newer, one the hiscores give no XP for as not known, the total level the larger of the hiscores' and the levels' sum, and Wise Old Man's EHP, EHB and hours to max), boss kills split from clues and other activities by Wise Old Man's boss metrics, quests grouped by status with their counts (filtered by status or part of a name), diaries per area and tier (one area also with its task names when known), combat achievement tiers (tasks, up to 50, only with a tier, status or name, as an account has over 600), the collection log as each tab's entries obtained of all (or one entry's items: up to 50 obtained, with counts and the day first obtained, and up to 100 missing by name, saying how many more), gains for a period or between two days in the user's zone (the latest 25 completed and 25 new collection log items, each by its day), the bank as its value, stacks and most valuable stacks (or what a search finds and where), and worn gear by slot with its bonuses that aren't 0 (from the wiki, one Bucket query per item, kept a day) and the inventory added up. The requirement checks and `calc_xp` fetch the hiscores first when they're past their freshness limit and say when the levels are from (`levelsFetchedAt`); `calc_xp` finds a skill by its name or Wise Old Man's (Runecrafting), names the account's skills when it's asked for one it hasn't, and says when the hiscores don't rank one. `find_gear_upgrades` reads `<boss>/Strategies` first, then the page named, gives every style's setup unless one is asked for, and leaves out the slots where what's owned is already the best. `search_wiki`'s results aren't listed as sources (no page was read); `get_wiki_page` takes a section by its index or its name, noting the page a redirect led to, and both it and the other knowledge tools note each page read. `list_goals` gives the active goals with their progress (the first five things each still needs, and how many more) and the ten done most recently; `add_goal` checks the goal with the shared schema (a custom one needs a title) before its Approve row is shown, and `update_goal` changes only this account's goals, its Approve row naming the goal (`Mark goal done: Reach 75 Magic`).

Only plain file names (letters, digits and `_().'%-`, ending `.png`) and numeric ids are accepted, so nothing can reach outside the folder. A file is written whole or not at all, and two pages asking for one icon share a fetch. An answer that isn't a PNG (a challenge page sent with a 200, say) is a failure. An icon the site doesn't have answers 404 with nothing written, isn't asked for again while the server runs, and the browser may keep that 404 for a day; any other failure answers 502, and that site isn't asked for any icon for a minute, so a page full of icons can't hold up the wiki's queue (which the chat's lookups share) during an outage. An icon that can't be written to disk is still served. The wiki file for a skill or boss is its name with spaces as underscores plus `_icon.png`, a colon turned into a hyphen as the wiki does; nine hiscores names whose icons the wiki names otherwise are listed (`Kree'Arra` → `Kree'arra_icon.png`, `Nightmare` → `The_Nightmare_icon.png`, ...). That's `wikiIconFile` in shared, with `WIKI_ICON_FILE`, the file-name pattern the server accepts. Checked against the wiki on 2026-10-27: all 24 skills and 62 of the 72 bosses have icons; the other ten (Chambers of Xeric, both Theatres of Blood, both Gauntlets, Phosani's Nightmare, Lunar Chests, Artio, Spindel, Calvar'ion) have none, so `<Icon>` leaves a blank of the icon's size, as it does for any icon that fails to load. The client shows them with `<Icon>`, pixel art kept sharp. Icons are Jagex's copyright ("used with permission" on the wiki), so they are never committed to the repo, and Settings credits "Game images © Jagex Ltd."

## Configuration

Settings that rarely change, and secrets, live in `.env` in the repo root, which is git-ignored. The committed `.env.example` lists every variable with its default and a one-line comment; copy it to `.env` to start. Everything else is a setting in the app.

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `CONTACT` | Yes | (none) | Discord name or email, sent in the User-Agent (`wise-old-model/<version> (personal use; contact: davisparkergoff@gmail.com)`) so Wise Old Man, Temple and the wiki can reach the user. Plain ASCII only, since it goes in an HTTP header |
| `PORT` | No | `4747` | Port the server listens on |
| `DATA_DIR` | No | The OS's app-data folder | Database, backups, icons and the Agent SDK's working folder |
| `RUNELITE_DIR` | No | `~/.runelite` | Where to find Character Export's files |
| `ANTHROPIC_API_KEY` | No | (none) | Only used when billing is set to API key |

The server checks these at startup and stops with a clear message when one is missing or invalid.

## Repo and tooling

- **npm workspaces:** `server/`, `client/` and `shared/` (the API's Zod schemas and types, used by both sides). `"engines": { "node": ">=26" }`.
- **Server:** Node 26 runs its TypeScript directly (built-in type stripping, no build step and no extra runner): `node --env-file-if-exists=.env server/src/main.ts`. In development `server/src/dev.ts` runs that and starts it again, once the old one has exited, whenever the server's or the shared code changes (tests excepted); it compares the files' modified times once a second, because Node's own `--watch` relies on file-change events, which a WSL checkout on a Windows drive never gets. Vite checks the client's files the same way (`server.watch.usePolling` in `client/vite.config.ts`), so a code change needs only a page reload. This allows only erasable TypeScript syntax (no enums, namespaces or parameter properties), so `tsconfig` sets `erasableSyntaxOnly` and `verbatimModuleSyntax`, and relative imports use `.ts` extensions.
- **Type checking:** TypeScript 7 (the native compiler) with `noEmit`; it never produces output.
- **Client:** in development the Vite dev server (port 5173) forwards `/api` to the server at `PORT` (read the way the server reads it: the environment, then the root `.env`). The proxy keeps the browser's `Host` (`changeOrigin: false`) so the local-only check still sees it, and Vite's CORS is off so pages on other localhost ports can't read API answers. In production `vite build` produces static files the server hosts, so the app is one process at one URL.
- **Lint and format:** Biome, one tool for both. It skips `server/test/fixtures`, so captured responses stay exactly as received. (ESLint's TypeScript plugin supports TypeScript only up to 6.0.)
- **Scripts:** `npm run dev` (server and Vite together, via `concurrently`), `npm run dev:server` and `npm run dev:client` (each alone), `npm run build` (the client), `npm start` (the app), `npm test`, `npm run typecheck`, `npm run lint`, and `npm run check` (type check, lint and tests; run before committing). A single test file: `npx vitest run <path>`.
- **Shared package:** `@wom/shared` exports only `shared/src/index.ts`, which re-exports every shared module.
- **Tests (Vitest 5):**
  - Unit: each source's parser (hiscores, Wise Old Man, Temple, Character Export, the wiki's requirement tables); every calculation (XP, requirements, gear upgrades, goal progress); the request handler's queues, rate limits and retries, with fake timers.
  - Integration: API routes against a temporary database (`testDb()`: in memory unless a test passes a file, with every migration applied, closed when the test finishes); the chat flow with a fake AI provider. Tests never call Claude.
  - Temporary folders: a test that needs one gets a fresh folder from `tempDir()` (`server/test/helpers.ts`), deleted when the test finishes, so tests never share leftovers and a full run leaves nothing behind.
  - Fixtures: real responses captured once from the public APIs. Character Export samples come from real files, trimmed and renamed so no real names or bank contents are committed.
  - Frontend: component tests only where there's logic (stream rendering, approvals, goal progress); no browser end-to-end tests. They fake the API with `client/src/test/fakeApi.ts`, where a request the fake doesn't serve fails the test, and use the app's own query client without retries. The test setup gives jsdom a `matchMedia` that reports a wide window. Tests with no DOM run in the node environment.
  - Vitest puts spies, stubbed globals and stubbed environment variables back before every test (`restoreMocks`, `unstubGlobals`, `unstubEnvs`), so tests don't undo them by hand.
- **Repo files:** `.gitignore` (`node_modules`, build output, coverage, `.env` and any `.env.*` except `.env.example`, `.superpowers/`, npm debug logs, `.DS_Store` and `Thumbs.db`); `.env.example`; `.gitattributes` forcing LF line endings so WSL and Windows agree.
- No CI and no git hooks: the user commits by hand.
